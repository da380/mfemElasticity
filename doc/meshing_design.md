# Meshing

*16 September 2026. Replaces the assessment and plan of 1 September 2026, whose outcome this records; the earlier text is in the git history of this file.*

## Where things stand

The C++ mesh generators that lived in `meshing/` (about 3150 lines against the gmsh SDK, built under `BUILD_GMSH`) have been removed, together with the CRUST-1.0 grids and the PREM deck in `data/`. Meshes are now generated by the Python scripts in `meshes/`, each a page long, which call the [planetmodel](https://github.com/da380/planetmodel) package (release 1.1.0 or later, `pip install 'planetmodel[meshing]'`). planetmodel is the model layer the September plan wanted to consolidate out of `common.cpp`, and its `mesh3d` sub-package is the mesher that plan described: concentric build, radius-sorted and named physical groups, per-interface sizing, orientation repair, curving, validation, MSH 2.2 plus a JSON manifest.

The eight gmsh meshes are no longer in the repository: they are generated into the build tree's `data/` by `meshes/CMakeLists.txt` (option `GENERATE_MESHES`, on with examples or tests; `MESHES_PYTHON` or an automatically created venv under the build directory supplies planetmodel). They are built at the resolution of the ones they replaced, and every attribute convention the examples and tests rely on is unchanged: layers 1..N and interfaces 1..M from the centre, the buffer last, the offset disc with 1 for the inclusion and 2 for its surroundings. Unlike the old meshes, the new ones load into MFEM with no orientation fixes.

## Division of labour

- **planetmodel** owns the model and the mesher: skeletons, geometries and mappings, the sizing rules, shells, the manifest schema and the MFEM export. Anything geometric that a new mesh here needs and planetmodel lacks is a planetmodel change, not a script here.
- **`meshes/`** owns the recipes: which skeleton, which sizes, which shells, which file name. It has no library of its own beyond `common.py`, and its `CMakeLists.txt` turns each recipe into a build step.
- **mfemElasticity** consumes `.msh` files from `data/` and, for now, keeps its positional attribute logic (`attributes.Max()` to tell the two- and three-layer Earth apart). A small C++ reader for the JSON manifest would let examples ask for layers by name; it is a follow-up, not a requirement.

## Deferred, and where it goes

- **CRUST-1.0 topography.** The old `geomesh_prem_crust` driver perturbed the nodes of a PREM mesh radially by interpolated crustal thickness and Moho depth, tapered with a cubic band. planetmodel expresses this as a radial displacement on a geometry, applied at the MFEM export with the folding check that the old code lacked; `meshes/aspherical_body.py` demonstrates the mechanism with a degree-2 formula, with and without a buffer shell across which the shape is tapered off. What is missing is a reader for lon–lat grids as a displacement; that belongs in planetmodel, and the grids return to `data/` (or a download step) when it exists.
- **PREM skeleton meshes** for the Love-number benchmark come from `PREM()` in planetmodel, coarsened as needed, through a script like `layered_earth.py`.
- **Recipes as data.** Mesh definitions are Python here. planetmodel 0.5 had a TOML recipe and a command line; if they return, the scripts collapse to files.

## Notes from the regeneration

- The old drivers' nominal sizes produced smaller elements than gmsh's Threshold fields do in planetmodel, so the scripts' sizes are 5–20 % smaller than the old command lines' to reach the same element counts.
- The three-layer 3D Earth is sensitive to the interface size: 0.15 gave one inverted tetrahedron at the linear stage, which planetmodel refuses, and 0.13, 0.145 and 0.16 each left one sliver (minSICN 0.004–0.015) after high-order optimisation. 0.135 gives minSICN 0.14. planetmodel runs gmsh's high-order optimiser but not the linear-mesh optimiser (`Mesh.Optimize` / Netgen), which is the likely fix on its side.
